# 👋 Welcome - start here Thanks for taking a look. This collection tests the e-commerce API end to end, and it is written so you can understand it by reading it, without opening a single script. Everything below takes about two minutes. --- ## Step 1 - make sure you imported both files There are two, and you need both: | File | What it is | |---|---| | `ecommerce-api-tests.postman_collection.json` | the tests (this file) | | `ecommerce-api-environment.postman_environment.json` | the settings they use | ## Step 2 - select the environment Top right of the Postman window there is a dropdown that says **No Environment**. Change it to **"E-Commerce API - Test Environment"**. > This is the only setup step, and it is the one people forget. If you see every > request failing with a strange address error, this dropdown is why. ## Step 3 - press Run Click the collection name in the sidebar → **Run** → **Run E-Commerce API - QA Test Suite**. The suite is 40 requests and 178 checks. The whole thing takes about 20 seconds. **There is nothing to fill in first.** No tokens to paste, no product ids to look up, no users to create by hand. The first folder registers its own accounts, logs them in, and stores the tokens automatically. Everything after that helps itself. --- ## 🟥 Please read this before you judge the results **Exactly 20 checks fail on purpose.** The suite is not broken - those failures are the whole point. The tests check what the API is *supposed* to do, not what it currently does. So each real problem shows up as a **failing test**, instead of being quietly recorded as if it were correct behaviour. Every request that is meant to fail is named `[BUG-1]`, `[BUG-2]` and so on, and the number points at the write-up in **BUGS.md**. > **The rule that matters: anything that fails WITHOUT a `[BUG-n]` tag is a genuine > new problem.** As of the last run there were none. --- ## 📖 How to read the request names | If the name starts with | It means | |---|---| | nothing special | A normal test. It should pass, and it does. | | `[BUG-n]` | ❌ **Fails on purpose.** It proves problem number `n` is real. | | `[QUESTION-n]` | ⚠️ Passes. Something I want a decision on, not a bug I am certain of. | | `[BY DESIGN]` | ✅ Passes. Looks like a bug, is not one. Explanation on the request. | ## 📂 What the folders do | Folder | What it covers | |---|---| | **01 - Setup - create our test users** | Creates the accounts everything else needs. **Run this first.** | | **02 - Register a new user** | The email rule, the password rule, and duplicate sign-ups | | **03 - Log in** | Where the most serious problem lives | | **04 - Products** | The response contract, and the `isDetailed` rule | | **05 - Orders - who is allowed to do what** | Tokens, and whether an order is actually yours | | **06 - Orders - things the API should refuse** | Bad baskets, bad quantities, bad JSON | | **07 - Orders - totals and stock** | Totals, stock levels, and ownership | Every folder and every request has its own **description tab** - like this one - explaining what it checks and why that is worth checking.
